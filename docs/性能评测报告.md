# MuMuShot 性能评测报告

**评测对象**：MuMuShot（截电脑屏幕 → 通过 adb 送进 MuMu 模拟器相册）
**对比版本**：Python 版（`python/mumu_shot.py` / `python/mumu_core.py`，PyInstaller 打包） vs **Rust 重写版**（`rust/`）
**报告日期**：2026-10-16

---

## 1. 结论摘要

| 维度 | 结论 |
| --- | --- |
| 发行体积 | **Rust 胜**：单文件 5.83 MB vs 39.29 MB / 996 个文件，小 **6.7 倍**，且免安装 |
| 命令行启动 | **Rust 胜**：`--selftest` 123 ms vs 234 ms，快 **1.9 倍** |
| 图形面板打开 | **Rust 胜**：面板可见 45 ms vs 762 ms，快约 **17 倍** |
| 全屏截图 + 编码 | **Rust 胜**：1080p 增量 29 ms vs 66 ms，快 2.3 倍 |
| 端到端上传 | **Rust 胜**：2738 ms vs 2867 ms，快 **5%** |
| 自动识别设备 | **两版相当**：Rust 170 ms vs Python 149 ms（都可忽略，见 §5） |
| 常驻内存（面板） | **Python 胜**：37.3 MB vs 98.5 MB，Rust 高 2.6 倍 |

一句话：**Rust 版在全部耗时指标上都更快（启动类 1.9 倍、面板 17 倍、端到端 5%），体积小 6.7 倍；代价是图形面板的内存占用更高。**

> 端到端只快 5%，是因为 2.7 秒里有约 2.5 秒花在 **adb 进程往返 + 模拟器媒体库索引** 上 —— 这部分与语言无关，换语言救不了。

**本轮还修掉了自动识别链路的一处真实缺陷**（§7.1、§7.4），两版同步受益：模拟器未启动时的失败路径从 **7.3 秒压到 0.53 秒（快约 13 倍）**，并且不再误报「没检测到实例」。

## 3. 指标口径与测量方法

数据由仓库内脚本自动采集，可复现：

```bash
# 命令耗时与体积（9 次取中位数，预热 2 次）
RUNS=9 bash bench/bench.sh
# 模拟器未启动时的失败路径（需先手动关闭模拟器）
bash bench/bench_norun.sh
# 图形面板常驻资源
powershell -ExecutionPolicy Bypass -File bench/mem.ps1
```

- **计时**：进程创建到退出的墙钟时间（毫秒）。每个用例预热 2 次，再连跑 9 次取**中位数**。
- **交替执行**：同一轮里两种实现都要跑，且奇偶轮交换先后顺序。端到端用例约有 ±10% 波动（adb 与模拟器响应在漂移），若先把一种实现跑完再跑另一种，漂移会整体算到某一方头上——实测会出现「截图更小的用例反而更慢」的假象。交替 + 双向排序可把漂移平摊到两边。
- **对等性**：除 `discover` 用例外，两版都用 `--device 127.0.0.1:16384` 显式指定设备，保证推送链路都成功、双方工作量一致。
- **体积**：可执行文件 + 必需依赖目录的字节数，不含日志与截图输出。
- **内存**：面板启动并静置 5 秒后读取工作集（WS）、私有内存、峰值工作集、线程数、句柄数。

### 派生量

| 派生量 | 计算方式 |
| --- | --- |
| 纯启动 | 直接读 `--selftest`（只做依赖/目录/日志检查） |
| 截图 + 编码增量 | `--full` − `--region 0,0,1,1`（两者都含连接与推送，差值即全屏抓取 + PNG 编码的额外开销） |
| 上传链路 | `--region 0,0,1,1` 减去纯启动 |
| 自动识别设备开销 | `--full`（自动找实例）− `--full --device`（显式指定），即第 2~4 级识别链路的净开销 |

> **误差说明**：端到端用例跨批次重复测量有约 ±10% 波动（受 adb / 模拟器响应与磁盘缓存影响）。本表为同一批次内的对比；`--selftest`、`--list-windows` 与内存指标波动小于 5%。表中数字为 2026-10-16 最终一批（交替执行，n=9）的中位数，原始数据见 `bench/results/raw.csv`。

## 5. 命令耗时（中位数，n=9）

| 用例 | Python | Rust | 提升 |
| --- | ---: | ---: | ---: |
| `--selftest`（纯启动） | 234 ms | **123 ms** | 1.90× |
| `--list-windows`（启动 + Win32 窗口枚举） | 161 ms | **114 ms** | 1.41× |
| `--region 0,0,1,1`（启动+连设备+微截图+推送+索引） | 2801 ms | **2709 ms** | 1.03× |
| `--full`（…+1080p 截图+编码） | 2867 ms | **2738 ms** | 1.05× |
| `--full` 自动识别设备（不给 `--device`） | 3016 ms | **2908 ms** | 1.04× |

**派生量**

| 派生量 | Python | Rust | 说明 |
| --- | ---: | ---: | --- |
| 全屏截图 + PNG 编码增量 | 66 ms | **29 ms** | 2.3× —— Rust 直接读 GDI 位图缓冲；Python 要经过 `PIL.ImageGrab` 对象构造与 `Image.save` 编码包装 |
| 上传链路（连设备→推送→索引） | 2567 ms | 2586 ms | 持平；这段是 adb 进程往返与媒体库索引，与语言无关 |
| 自动识别设备开销 | 149 ms | 170 ms | 见下 |

**关键观察**

- 纯启动差 1.9 倍：Python 要加载解释器 + Tcl/Tk + PIL；Rust 是原生单文件。
- 端到端 2.7 秒里，**约 2.5 秒花在 adb 进程往返与媒体库索引上**。这部分与语言无关，所以整体只拉开 5%。
- **自动识别模拟器端口的开销只有 0.15~0.17 秒**（走 MuMuManager 那一级），完全不需要为了省时间而写死 `--device`；两版都能默认全自动。
- `--region 0,0,1,1` 与 `--full` 的差距就是截图与编码的开销：Rust 29 ms、Python 66 ms。注意这两个用例本身的推送链路占了 2.6 秒，所以截图部分的 2.3 倍优势在端到端里会被稀释。

## 6. 图形面板常驻资源

| 指标 | Python 版 | Rust 版 |
| --- | ---: | ---: |
| 面板可见耗时（热启动） | 762 ms | **45 ms** |
| 工作集 WS | **37.3 MB** | 98.5 MB |
| 私有内存 Private | **19.7 MB** | 62.2 MB |
| 峰值工作集 | **37.3 MB** | 99.4 MB |
| 线程数 | **6** | 13 |
| 句柄数 | **194** | 276 |

**为什么 Rust 面板更吃内存？**

1. egui / OpenGL 渲染栈本身要维护 GPU 缓冲区与字形图集；
2. Rust 版在进程内加载了完整中文字体 `C:\Windows\Fonts\msyh.ttc`（微软雅黑，约 19 MB）并常驻解析结果；Python 版直接借用系统字体栈，进程内不留字体文件；
3. 每次截图会新建一张全屏 RGBA 缓冲（1080p ≈ 8 MB）用于编码，尚未做缓冲复用。

**可选优化（尚未实施）**：中文字体子集化或改用系统字体提供器、复用截图缓冲、按需释放字形图集。预期可把私有内存压到 40 MB 以内。

需要说明的是，**命令行路径完全不涉及这些开销** —— `--full` 的峰值内存与 Python 版同量级。

## 7. 移植中发现的问题

Rust 版是**逐行对照仓库里的 `python/mumu_shot.py` / `python/mumu_core.py`** 写的。对拍过程中发现并处理了 4 个问题，其中 §7.1 / §7.4 是自动识别链路本身的缺陷，**参考实现与 Rust 版都受影响，已两版一起修**：

### 7.1 端口嗅探兜底会白等非 adb 端口（参考实现本身的问题）

`pick_device` 的兜底链路是：显式设备 → MuMuManager 实例端口 → **扫进程监听端口** → 常见端口 → `adb devices`。

第三级原来把「MuMu 进程名 + 本地监听」的端口全收，而 MuMu 除客户机进程外还跑着远程服务、主控等多个进程，它们持有的是自家 RPC 端口：

| 端口 | 持有进程 | 是不是 adb 端口 |
| --- | --- | --- |
| 5555 / 7555 / 16384 | `MuMuNxDevice.exe`（客户机） | **三个都是** |
| 37640 / 45582 | `MuMuRemoteBackend.exe` | 不是 |
| 1026 / 11172 | `MuMuRemoteService.exe` 等 | 不是 |

而 `adb connect` 打到非 adb 端口会一直等到握手超时：

| 探测对象 | 耗时 |
| --- | ---: |
| 真 adb 端口（16384） | 136 ms |
| 监听中但不是 adb（37640） | **10122 ms** |
| 没有进程监听（9999） | 2120 ms |

候选最多 8 个、每个上限 6 秒 → **最坏白等约 48 秒**。

> **更正一处早先的判断。** 本报告此前写过「5555 是 MuMu 其他服务占用的端口，连上去 `getprop` 也成功，但 `push` 必然失败」。实测后确认不成立：5555 / 7555 / 16384 由**同一个客户机进程** `MuMuNxDevice.exe` 持有，**三个都是可用的 adb 端口**——都能取到 `release=15`、`model=2206123SC`，也都能成功写入 `/sdcard/Pictures`。早先那次 `push` 失败的真正原因当时未定位、事后也没能复现，可以确定的是**与端口选择无关**。Rust 版照搬参考逻辑，所以两版同样存在下面这条真实缺陷。

### 7.2 `adb push` 目标写成"目录 + 斜杠"会把文件名截短

Rust 版初版把 `adb push` 的目标写成 `/sdcard/Pictures/MuMuShot/`（带尾斜杠的目录），让 adb 自己从本地路径推导远端文件名。而截图目录的绝对路径里含中文（`...\Desktop\项目集合\MuMuShot\...`），adb 推导时出错，设备上落地的文件名被截短：

```
期望：Shot_20261016_195659.png
实际：Shot_20261016_1956
```

内容正确、字节数一致，但文件名残缺，媒体库按名匹配失败、图库看不到。

**修复**：改成与 Python 版一致 —— **把完整目标路径显式传给 adb**；同时为彻底避开非 ASCII 参数，把工作目录切到截图所在目录、只传相对文件名：

```
cwd = <shots 目录>
adb -s <serial> push Shot_20261016_195659.png /sdcard/Pictures/MuMuShot/Shot_20261016_195659.png
```

> Python 版一直传的就是完整目标路径，所以从没踩到这个坑 —— 这也解释了为什么同样的机器上 Python 一直正常。

### 7.3 媒体库索引需要等待

刚 `push` 完立刻查 MediaStore 往往查不到（索引有延迟）。参考实现是 **6 次 × 0.8 秒** 轮询；Rust 版初版只查一次就放弃，会误报"媒体库暂未索引"。已改成与参考实现相同的节奏。

### 7.4 自动识别链路的加固与提速（两版同步）

针对 §7.1，两版一起改了四处。原则是 **收紧判定，但不增加任何一次 adb 往返**：

| # | 改动 | 效果 |
| --- | --- | --- |
| 1 | 候选先按**进程身份**筛，再谈连接：客户机进程持有的端口全收，其它 MuMu 进程持有的必须本身就是常用 adb 端口 | 37640 / 45582 这类在**调用 adb 之前**就被剔掉，不再白等 |
| 2 | 猜来的端口用**短握手超时**（2 秒，原来 6 秒）：真 adb 端口毫秒级应答，非 adb 端口要 10 秒才失败，2 秒足够区分 | 最坏从 48 秒降到 16 秒；实际候选通常只剩 3 个 |
| 3 | 判定加严且**不额外往返**：原来只问 `getprop ro.build.version.release`，现在把「取 Android 版本号 + 探目标存储」合并进**同一次 shell 调用**，要求设备既能报出版本、又有 `/sdcard/Pictures` 才当候选 | 判定更严，往返次数不变 |
| 4 | 修掉一处**提前退出失效**：实例未启动时 MuMuManager 不返回 `adb_port` 字段，原实现据此认为"没有实例"，于是"确认实例状态后就不猜端口"这条捷径从不生效，转而把常见端口猜一遍 | 失败路径从 7 秒级降到 0.6 秒级 |

**效果：模拟器未启动时的失败路径**

复现脚本 `bench/bench_norun.sh`（需先手动关闭模拟器）。同一台机器、同一份 adb：

| 实现 | 改前 | 改后 | 提升 |
| --- | ---: | ---: | ---: |
| Rust | 7270 ms（n=3） | **530 ms**（n=5） | 13.7× |
| Python | 7215 ms（n=3） | **537 ms**（n=5） | 13.4× |

改前数据取自**改动前的构建**（Rust 用冻结的改前二进制，Python 用改动前的打包 exe）；改后数据由脚本现场采集，原始数据见 `bench/results/norun.csv`。

顺带修正了报错文案：改前报「没检测到运行中的 MuMu 实例」（与事实不符——实例是存在的，只是没启动），改后报「MuMu 模拟器没在运行（或正在启动/关闭中）」。两版退出码都是 3。

**效果：第 3 级逐个候选的判定**（模拟器运行中，`cargo test --release -- --ignored --nocapture`）

| 候选端口 | 归属 | 判定 | 耗时 |
| --- | --- | --- | ---: |
| 5555 / 7555 / 16384 | 客户机（真 adb） | 接受 | 95–106 ms |
| 23576 / 24576 | 客户机（非 adb） | 拒绝 | 2.05 s |
| 37640 / 45582 / 1026 / 11172 | 非客户机 | — | 不进入探测 |

**回归防护**：Rust 侧新增 3 个单元测试（候选筛选：客户机/非客户机/去重限流）+ 2 个真机测试（默认忽略，`--ignored` 手动跑）；`bench/bench.sh` 增加 `discover` 用例，把"自动识别设备"的开销从端到端里单独隔离出来。

```bash
cargo test --release                                    # 纯逻辑，随时可跑
cargo test --release -- --ignored --nocapture           # 真机：逐个候选端口的判定与耗时
```

## 9. 已知差异与局限

**已知差异（均不影响使用）**

- Rust 版界面用 egui 绘制，观感与 tkinter 不完全相同（尺寸、文案、状态栏颜色已对齐）。
- 框选遮罩：Rust 版用半透明黑覆盖实现整屏压暗，Python 版直接把底图亮度调到 42%，视觉效果接近但不逐像素相同。
- 字体：Rust 版显式加载微软雅黑；Python 版用系统字体栈。

**测量局限**

- 仅在一台低压 U 系列 + 集显机器上测过，未覆盖多显示器、其他缩放档位（100% / 150%）。
- 端到端用例跨批次波动约 ±10%（adb 与模拟器响应主导），已用交替执行 + 双向排序缓解，但仍不是严格的双盲对照。
- 图形面板内存只测了单次静置快照，未做长时间运行的泄漏观察。
- `--snip`（调起系统截图工具）依赖人工框选，属交互路径，未纳入自动计时。
- 自动识别的失败路径只覆盖了「模拟器未启动」一种；「MuMu 正在启动中」「多开实例切换」两种状态靠逻辑推断，未做定量测量。

**后续建议**

1. 面板内存：字体子集化 + 截图缓冲复用（见 §6）。
2. `--snip` 与"截图瞬间隐藏面板"两条交互路径补人工验收。
3. 若想继续压端到端耗时，方向不是语言，而是**减少 adb 进程往返**（合并 mkdir / chmod / 索引），或改用 adb 长连接协议直接通信。
4. `MuMuManager info` 的字段（`adb_port` / `is_android_started` / `adb_host_ip`）若随版本变化，需同步维护解析。注意 `adb_port` 只在实例运行时出现，判断"有没有实例"不能只看这个字段（§7.4 第 4 条）。
5. 端口嗅探的第 3 级目前只按进程身份 + 常用端口表筛；若要支持非 MuMu 的模拟器（雷电、BlueStacks…），需要为其补一套进程识别规则。
