# MuMuShot 性能评测报告

**评测对象**：MuMuShot（截电脑屏幕 → 通过 adb 送进 MuMu 模拟器相册）
**对比版本**：Python 版（`mumu_shot.py` / `mumu_core.py`，PyInstaller 打包） vs **Rust 重写版**（`rust/`）
**报告日期**：2026-10-16

---

## 1. 结论摘要

| 维度 | 结论 |
| --- | --- |
| 发行体积 | **Rust 胜**：单文件 5.82 MB vs 39.29 MB / 996 个文件，小 **6.7 倍**，且免安装 |
| 命令行启动 | **Rust 胜**：`--selftest` 137 ms vs 279 ms，快 **2.0 倍** |
| 图形面板打开 | **Rust 胜**：面板可见 45 ms vs 602 ms，快约 **13 倍** |
| 全屏截图 + 编码 | **Rust 胜**：1080p 增量 57 ms vs 186 ms |
| 端到端上传 | **Rust 胜**：2858 ms vs 3128 ms，快 **9%** |
| 常驻内存（面板） | **Python 胜**：35.0 MB vs 99.0 MB，Rust 高 2.8 倍 |

一句话：**Rust 版在全部耗时指标上都更快（启动类 2 倍、面板 13 倍、端到端 9%），体积小 6.7 倍；代价是图形面板的内存占用更高。**

> 端到端只快 9%，是因为 2.9 秒里有约 2.5 秒花在 **adb 进程往返 + 模拟器媒体库索引** 上 —— 这部分与语言无关，换语言救不了。

## 3. 指标口径与测量方法

数据由仓库内脚本自动采集，可复现：

```bash
# 命令耗时与体积（9 次取中位数，预热 2 次）
RUNS=9 bash bench/bench.sh
# 图形面板常驻资源
powershell -ExecutionPolicy Bypass -File bench/mem.ps1
```

- **计时**：进程创建到退出的墙钟时间（毫秒）。每个用例预热 2 次，再连跑 9 次取**中位数**。
- **对等性**：两版都用 `--device 127.0.0.1:16384` 显式指定设备，保证推送链路都成功、双方工作量一致。
- **体积**：可执行文件 + 必需依赖目录的字节数，不含日志与截图输出。
- **内存**：面板启动并静置 5 秒后读取工作集（WS）、私有内存、峰值工作集、线程数、句柄数。

### 三个派生量

| 派生量 | 计算方式 |
| --- | --- |
| 纯启动 | 直接读 `--selftest`（只做依赖/目录/日志检查） |
| 截图 + 编码增量 | `--full` − `--region 0,0,1,1`（两者都含连接与推送，差值即全屏抓取 + PNG 编码的额外开销） |
| 上传链路 | `--region 0,0,1,1` 减去纯启动 |

> **误差说明**：端到端用例跨批次重复测量有约 ±10% 波动（受 adb / 模拟器响应与磁盘缓存影响）。本表为同一批次内的对比；`--selftest`、`--list-windows` 与内存指标波动小于 5%。

| | Python 版 | Rust 版 | 对比 |

## 5. 命令耗时（中位数，n=9）

| 用例 | Python | Rust | 提升 |
| --- | ---: | ---: | ---: |
| `--selftest`（纯启动） | 279 ms | **137 ms** | 2.0× |
| `--list-windows`（启动 + Win32 窗口枚举） | 194 ms | **116 ms** | 1.7× |
| `--region 0,0,1,1`（启动+连设备+微截图+推送+索引） | 2942 ms | **2801 ms** | 1.05× |
| `--full`（启动+连设备+1080p 截图+编码+推送+索引） | 3128 ms | **2858 ms** | 1.09× |

**关键观察**

- 纯启动差 2 倍：Python 要加载解释器 + Tcl/Tk + PIL；Rust 是原生单文件。
- 全屏截图 + PNG 编码的增量是 **57 ms（Rust）/ 186 ms（Python）**，差 3 倍多 —— Rust 直接读 GDI 位图缓冲，Python 要经过 `PIL.ImageGrab` 的对象构造与 `Image.save` 的编码包装。
- 端到端 2.9 秒里，**约 2.5 秒花在 adb 进程往返与媒体库索引上**。这部分与语言无关，所以整体只拉开 9%。

## 6. 图形面板常驻资源

| 指标 | Python 版 | Rust 版 |
| --- | ---: | ---: |
| 面板可见耗时（热启动） | 602 ms | **45 ms** |
| 工作集 WS | **35.0 MB** | 99.0 MB |
| 私有内存 Private | **19.6 MB** | 62.7 MB |
| 峰值工作集 | **35.0 MB** | 99.9 MB |
| 线程数 | **6** | 13 |
| 句柄数 | **169** | 276 |

**为什么 Rust 面板更吃内存？**

1. egui / OpenGL 渲染栈本身要维护 GPU 缓冲区与字形图集；
2. Rust 版在进程内加载了完整中文字体 `C:\Windows\Fonts\msyh.ttc`（微软雅黑，约 19 MB）并常驻解析结果；Python 版直接借用系统字体栈，进程内不留字体文件；
3. 每次截图会新建一张全屏 RGBA 缓冲（1080p ≈ 8 MB）用于编码，尚未做缓冲复用。

**可选优化（尚未实施）**：中文字体子集化或改用系统字体提供器、复用截图缓冲、按需释放字形图集。预期可把私有内存压到 40 MB 以内。

需要说明的是，**命令行路径完全不涉及这些开销** —— `--full` 的峰值内存与 Python 版同量级。

## 7. 移植中发现的问题

Rust 版是**逐行对照仓库里的 `mumu_shot.py` / `mumu_core.py`** 写的。对拍过程中发现并处理了 3 个问题：

### 7.1 端口嗅探兜底会连到非 adb 端口（参考实现本身的问题）

`pick_device` 的兜底链路是：显式设备 → MuMuManager 实例端口 → **扫进程监听端口** → 常见端口 → `adb devices`。

第三级按「MuMu 进程名 + 本地监听 + 端口在常见 adb 端口表里」筛选，而 **5555 也在那张表里**。当 MuMuManager 没能及时应答时，就会匹配到 MuMu 其他服务占用的 5555，连上去 `getprop` 也照样成功，于是"连上了"，但后续 `adb push` 必然失败：

```
adb: error: failed to copy ... remote secure_mkdirs() failed: No such file or directory
```

实测出现过一次（MuMuManager 那一级没返回结果时）。**这是参考实现固有的薄弱点，Rust 版按原逻辑照搬，所以两版都会遇到**，不是移植引入的偏差。要根治的话，应该在端口嗅探后补一次"这端口是不是真 adb 端口"的判定，而不是只看能不能 `getprop`。

### 7.2 `adb push` 目标写成"目录 + 斜杠"会把文件名截短

Rust 版初版把 `adb push` 的目标写成 `/sdcard/Pictures/MuMuShot/`（带尾斜杠的目录），让 adb 自己从本地路径推导远端文件名。而截图目录的绝对路径里含中文（`...\Desktop\项目集合\MuMuShot\...`），adb 推导时出错，设备上落地的文件名被截短：

```
期望：Shot_20261016_195659.png
实际：Shot_20261016_1956
```

内容正确、字节数一致，但文件名残缺，媒体库按名匹配失败、图库看不到。

**修复**：改成与 Python 版一致 —— **把完整目标路径显式传给 adb**；同时为彻底避开非 ASCII 参数，把工作目录切到截图所在目录、只传相对文件名：

```
cwd = <shots 目录>
adb -s <serial> push Shot_20261016_195659.png /sdcard/Pictures/MuMuShot/Shot_20261016_195659.png
```

> Python 版一直传的就是完整目标路径，所以从没踩到这个坑 —— 这也解释了为什么同样的机器上 Python 一直正常。

### 7.3 媒体库索引需要等待

刚 `push` 完立刻查 MediaStore 往往查不到（索引有延迟）。参考实现是 **6 次 × 0.8 秒** 轮询；Rust 版初版只查一次就放弃，会误报"媒体库暂未索引"。已改成与参考实现相同的节奏。

## 8. 功能对等性验证

Rust 版逐条路径实测（同一 MuMu 实例，返回 `media id` 视为完整成功）：

| 路径 | 结果 |
| --- | --- |
| `--selftest` | 通过（截图模块 / 目录可写 / 日志可写 / 窗口枚举），输出 `selftest ok` 供 CI 匹配 |
| `--list-windows` | 通过（`  {宽:>5}×{高:<5}  {标题}`，与 Python 输出格式一致） |
| `--full` | 通过（1920×1080 → 推送 → 索引 `media id`） |
| `--region 0,0,1,1` | 通过（固定区域，留档名 `Region_*.png`） |
| `--region`（交互框选） | 通过（覆盖层 1920×1080 全屏；模拟拖拽后裁出的图像与物理拖拽范围**逐像素一致**） |
| `--clipboard` | 通过（从剪贴板读出 64×48 位图并上传，留档名 `Clip_*.png`） |
| `--window 关键词` | 通过（截出 1466×921 的窗口，留档名 `Win_*.png`） |
| `--console` | 通过（`Ctrl+Alt+A/Q/S/C` 逐条 ✓ 输出，与 Python 一致） |
| 图形面板 | 通过（410×400、置顶；按钮文案带热键后缀、两个复选框、绿色状态栏、底部留档路径） |

**退出码也已对齐**（便于做快捷方式 / 脚本判断）：

| 场景 | 退出码 |
| --- | --- |
| 成功 | 0 |
| `--region` 格式错误 | 2 |
| 连不上 adb / 设备 | 3 |
| 截图或推送失败 | 4 |
| `--window` 没匹配到窗口 | 5 |

> 交互框选的验证方式：脚本用 `SetCursorPos` + `mouse_event` 模拟一次真实拖拽（125% 缩放下物理位移 875×575），覆盖层裁出的图像正好是 875×575，随后自动完成推送与索引。

## 9. 已知差异与局限

**已知差异（均不影响使用）**

- Rust 版界面用 egui 绘制，观感与 tkinter 不完全相同（尺寸、文案、状态栏颜色已对齐）。
- 框选遮罩：Rust 版用半透明黑覆盖实现整屏压暗，Python 版直接把底图亮度调到 42%，视觉效果接近但不逐像素相同。
- 字体：Rust 版显式加载微软雅黑；Python 版用系统字体栈。

**测量局限**

- 仅在一台低压 U 系列 + 集显机器上测过，未覆盖多显示器、其他缩放档位（100% / 150%）。
- 未测量"模拟器未启动"失败路径的耗时（涉及固定重试等待，两版策略相同）。
- 图形面板内存只测了单次静置快照，未做长时间运行的泄漏观察。
- `--snip`（调起系统截图工具）依赖人工框选，属交互路径，未纳入自动计时。

**后续建议**

1. 面板内存：字体子集化 + 截图缓冲复用（见 §6）。
2. `--snip` 与"截图瞬间隐藏面板"两条交互路径补人工验收。
3. 若想继续压端到端耗时，方向不是语言，而是**减少 adb 进程往返**（合并 mkdir / chmod / 索引），或改用 adb 长连接协议直接通信。
4. §7.1 的端口嗅探兜底建议加一道"是否真为 adb 端口"的校验（两版都受益）。
5. `MuMuManager info` 的字段（`adb_port` / `is_android_started` / `adb_host_ip`）若随版本变化，需同步维护解析。
